PART 3  HOW IT WORKS (STEP BY STEP)
====================================================================

--------------------------------------------------------------------
3.1  First run
--------------------------------------------------------------------

  1. Copy .env.example to .env, fill in at least SECRET_KEY and
     DB password. Everything else can stay in mock mode.
  2. docker compose up --build
  3. The api container runs migrations and the seed script:
     20 services, 11 agents, an admin account, a demo client and a
     few demo requests.
  4. Open http://localhost:8000
       /              landing page
       /services/...  service pages
       /login         sign in
       /portal        client portal (login as demo client)
       /admin         admin dashboard (login as admin)
       /docs          Swagger API docs

--------------------------------------------------------------------
3.2  Visitor to client
--------------------------------------------------------------------

  Visitor reads landing page -> clicks a service page -> clicks
  "Start a request" or "Subscribe" -> registers -> picks a plan ->
  pays (Stripe, or instant in mock mode) -> subscription row created
  -> Onboarding Agent runs: creates the client's Google Drive folder
  (or local folder), creates a welcome support ticket and chat
  message asking for brand assets -> you get a notification "New
  client: Acme".

  A visitor who only fills the contact form becomes a row in
  lead_database with source = "website" and you get a "New lead"
  notification.

--------------------------------------------------------------------
3.3  A request, end to end
--------------------------------------------------------------------

  1. Client opens the portal, picks "YouTube Thumbnail Design".
     The form shown comes from that service's form_schema, so each
     service asks its own questions (video title, channel, style...).
  2. Client submits, optionally attaches files.
  3. Backend creates the service_request (status = pending), stores
     files, writes an audit row, creates a notification for the
     admin tagged with the service, and publishes an event.
  4. Within milliseconds your admin dashboard (if open) receives the
     event over WebSocket: the bell goes from 11 to 12, the
     "YouTube Thumbnail" item in the services menu goes from (5) to
     (6) and flashes, a toast appears, and the request card shows up
     at the top of that service's board.
  5. You click [Accept]. One API call: status -> accepted, DB updated
     instantly, client gets a notification and sees the status
     change live in their portal. The request is queued for the
     agent pipeline.
  6. Worker picks it up and runs the LangGraph:
       Project Manager  reads the brief, sets priority, writes a
                        task plan, status -> in_progress
       Strategy         researches the client's brand notes and
                        competitors, writes direction
       Content          writes headline / caption / copy options
       Design           writes detailed design concepts and
                        (if an image provider is configured)
                        generates draft images; saved as designs v1
       QA               checks the output against the brief and brand
                        assets, scores it, flags issues; may send it
                        back to Design once
       Admin Approval   graph pauses (LangGraph interrupt). Status
                        -> review. You get a notification "Ready for
                        your review". You open it, see the concepts,
                        upload your final files (or approve AI
                        drafts), click Approve.
       Delivery         creates the delivery, uploads final files to
                        the client's Drive folder, generates download
                        links, notifies the client.
  7. Client downloads, or clicks "Request revision" and writes
     feedback.
  8. Revision Agent summarises the feedback into concrete change
     items, creates revision round 2, re-enters the Design -> QA ->
     Approval -> Delivery loop.
  9. When the client (or you) marks it done, status -> completed,
     analytics snapshot updates, counts drop.

  Every step writes an agent_logs row so the Control Center and
  the request timeline show exactly what happened.

  You can also skip the agents entirely: Accept, do the work
  yourself, upload files, click [Completed]. The buttons work
  independently of the AI.

--------------------------------------------------------------------
3.4  Notifications
--------------------------------------------------------------------

  One function, notify(user, type, title, body, link, service_id),
  is called from everywhere (new request, revision, upload, payment,
  lead, agent needs approval, chat message). It inserts the row and
  publishes to Redis. The api process is subscribed and forwards to
  every open WebSocket of that user. The bell count is simply the
  number of unread rows. Clicking the bell opens the panel; clicking
  an item marks it read, navigates to the link, and the count drops.
  "Mark all read" exists too. The services menu badges use the same
  mechanism with a different event type.

--------------------------------------------------------------------
3.5  AI Agent Control Center
--------------------------------------------------------------------

  The agents table holds one row per agent. The worker loop:
    - polls a Redis queue for jobs (request pipeline, lead run,
      marketing post, etc.)
    - before each step checks the agent's status; "paused" waits,
      "stopped" aborts the run cleanly and records it
    - updates current_activity, last_run_at, tasks_completed,
      success_rate after each step and publishes agent_status events
  The Control Center page shows all 11 cards live, with the four
  buttons calling POST /agents/{key}/start|pause|stop|restart.
  Each card expands to show the last 50 log lines.

  Scheduled agents (Lead, Outreach follow-ups, Marketing posts) run
  on a schedule you set in the admin UI (default: Lead daily,
  Marketing 3x/week, Outreach follow-ups every morning). Scheduling
  is done by the worker using APScheduler, so no external cron.

--------------------------------------------------------------------
3.6  Security
--------------------------------------------------------------------

  - Passwords hashed with bcrypt (passlib).
  - JWT access token (15 min) + refresh token (7 days, stored and
    revocable). Sent as Authorization: Bearer.
  - Roles enforced per endpoint. Clients can only ever see their own
    rows (enforced in queries, not just the UI).
  - Pydantic validation on every request body.
  - Rate limiting (slowapi): strict on login/register/contact, normal
    elsewhere.
  - Uploads: whitelist of extensions and MIME types, size limit,
    random stored filenames, never served from an executable path,
    content-type sniffing.
  - Every write by an admin and every status change is in audit_logs.
  - CORS locked to the app origin, secure headers middleware.

--------------------------------------------------------------------
3.7  Billing
--------------------------------------------------------------------

  Three plans (Starter / Pro / Premium) with monthly price, number
  of active requests at a time, and turnaround promise. Checkout
  goes to Stripe Checkout; the Stripe webhook updates subscriptions
  and inserts payments rows and a "New payment received"
  notification. In mock mode, "Subscribe" activates immediately so
  you can test the whole flow without a Stripe account. Invoices are
  listed in the portal from the payments table.
